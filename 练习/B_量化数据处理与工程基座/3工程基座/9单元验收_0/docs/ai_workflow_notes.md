## 一、AI 在我的学习中扮演了什么角色？

### 🎯 三个核心角色

| 角色 | 什么时候 AI 最好用 | 什么时候不好使 |
|------|-------------------|---------------|
| **代码翻译机** | "把 print 换成 logging"、"给这个函数加类型注解" | 代码太长时 AI 会漏改 |
| **测试生成器** | "给 clean_df 写 5 个测试，覆盖边界情况" | 默认只写"正常情况"，不会主动想边界 |
| **架构参谋** | "这个项目拆几个模块合适？" | 过度设计——3 个文件的事拆成 10 个文件 |

### 🔄 一条"AI 辅助开发"的标准流水线（我已形成习惯）

```
1. 我：想清楚"这个函数要干什么，输入输出是什么"
2. AI：生成第一版代码
3. 我：审 —— 类型注解对吗？边界情况处理了吗？命名合理吗？
4. 我：把代码跑起来，看两三个真实输入 → 输出
5. AI：写测试
6. 我：跑测试 → 修不通过的
7. AI：ruff format + ruff check，修 lint 问题
8. 我：git add → git commit（message 自己写！）
```

## 二、哪些时候 AI 很有用？（5 个最佳场景）

### ✅ 1. 样板代码生成
**场景**：logging 配置、argparse 解析器、项目骨架（pyproject.toml、.gitignore）
**为什么好用**：模板化、不需要创意、人类写了也记不住
**提示词范例**：`"帮我配置 logging，INFO 级别，格式带时间戳，输出到终端"`

### ✅ 2. 类型注解批量添加
**场景**：给已经能跑的代码加全部类型注解
**为什么好用**：机械劳动，AI 比人快 10 倍，且不会漏
**提示词范例**：`"给这个文件里所有函数加上类型注解，参数和返回值都要"`

### ✅ 3. 测试用例生成
**场景**：写完函数 → AI 写一个覆盖 5 种情况的测试文件
**为什么好用**：AI 不会只写"正常情况"（如果你明确要求边界）
**提示词范例**：`"写 5 个测试，覆盖：正常数据、空数据、有 NaN、全是 NaN、极端大值"`

### ✅ 4. Lint 问题批量修复
**场景**：ruff check 报 30 个问题 → AI 解释每个是什么 → AI 批量修
**为什么好用**：省 token（不需要我逐个理解规则）
**提示词范例**：`"ruff check 报的这些错误，帮我解释每个是什么问题，然后修掉"`

### ✅ 5. 项目结构设计讨论
**场景**："这个函数应该拆到哪个模块？" / "src/ 布局还是 flat 布局？"
**为什么好用**：AI 能解释每种选择的 trade-off，而不是给一个"标准答案"
**提示词范例**：`"这个项目应该用 src layout 还是 flat layout？各有什么优缺点？"`

## 三、哪些时候 AI 帮了倒忙？（4 个教训）

### ❌ 1. 代替我理解代码
**场景**：AI 解释了某段代码，我就"懂了"，但实际没懂
**教训**：AI 的解释必须用自己的话重述一遍，否则就是假懂
**对策**：看完 AI 解释后，关掉聊天窗口，自己写一行注释总结

### ❌ 2. 连续"修复"不验证
**场景**：AI 改了 A → 我没跑测试 → 又叫 AI 改 B → B 改坏了 A 修好的东西
**教训**：每改一次就要跑一次测试，不能攒一堆修改一起跑
**对策**：严格执行"改 → 跑测试 → commit → 改下一样"

### ❌ 3. 过度依赖 AI 写 commit message
**场景**：让 AI 生成 commit message → 三周后看 git log，完全不知道每次改了什么
**教训**：commit message 是写给三个月后的自己看的，AI 不知道你的意图
**对策**：AI 可以提建议，但最终 message 必须是自己的话

### ❌ 4. 不审就直接执行
**场景**：AI 生成了一段 bash 命令（比如 `git reset --hard`），没仔细看就执行了
**教训**：AI 的命令必须一行行审——特别是带 `--hard`、`--force`、`rm -rf` 的
**对策**：养成习惯：任何有破坏性的命令，停下来、读一遍、再决定是否执行

## 四、我的"AI 协作法则"（已形成肌肉记忆的 5 条）

### 法则 1：永远做"最后审稿人"
> AI 出代码 = 实习生交作业。你不需要替实习生写，但你必须能看出他哪里写错了。

### 法则 2：run before trust
> AI 改完 → 立刻跑测试。不通过 → 不给 AI 继续改别的。通过 → commit，再继续。

### 法则 3：自己的 commit message 自己写
> commit 记录的是"我为什么做这个改动"，不是"AI 改了什么"。AI 不知道你为什么。

### 法则 4：破坏性命令，默念 3 秒再执行
> `git reset --hard`、`rm -rf`、`DROP TABLE`——看到一个，停下来三秒。

### 法则 5：语法可以忘，判断力不能外包
> `pyproject.toml` 的精确格式，每次让 AI 写就行。但 "pytest 测试应该拆成几个文件"、"这个函数的类型注解写错了吗"、"为什么 ruff check 报这个错"——这些判断必须留在自己脑子里。

## 五、工具链：什么场景该叫 AI 干什么

```
项目启动
  │
  ├─→ "uv init + pyproject.toml"              ← AI（模板化）
  ├─→ ".gitignore"                             ← AI（模板化）
  │
代码编写
  │
  ├─→ "给函数加类型注解"                       ← AI（机械劳动）
  ├─→ "把这个 print 换成 logging"             ← AI（正则替换）
  │
每完成一个函数
  │
  ├─→ "写 pytest 测试，覆盖边界情况"            ← AI（测试生成）
  ├─→ git add + git commit                    ← 自己（10 秒的事）
  │
代码质量
  │
  ├─→ uv run ruff format .                    ← 自己（一条命令）
  ├─→ uv run ruff check . --select=ALL        ← 自己（一条命令）
  ├─→ "解释这些 lint 报错，然后修掉"            ← AI（批量修复）
  │
出 bug 了
  │
  ├─→ git diff                                ← 自己
  ├─→ "这段 diff 帮我看，问题在哪"              ← AI（辅助诊断）
  │
```

## 六、未来两周想挑战的"AI 协作高级用法"

1. **让 AI 写 code review**：PR 提交前让 AI review 一遍 diff，找低级错误
2. **让 AI 写 docstring**：给每个函数自动生成 Google 风格 docstring
3. **让 AI 帮我重构**："把 run_pipeline 的返回从 tuple 改成 NamedTuple"
4. **mypy 类型检查**：让 AI 跑 mypy，解释报错，修复类型不一致
5. **让 AI 做覆盖率分析**：`pytest --cov`，告诉 AI "哪些分支没测到"，让它补用例
