# mvp思维
> mvp思维，(minimum viable product)。  
> 经过详细的产品规划后下一步就要测试。方法则是：‘最小可行性产品’，通过这种方法进行实测
## 误区
- 正确
    - 测试验证的是‘需求’
- 错误
    - 上来就开始想要有什么功能这个产品才能完备，出发点错了
> 验证的是需求，所以产品的功能要以这样的思路设计：
```
确定自己验证的目的：一种需求是否存在
↓
根据这种需要被验证的需求设计功能
#重点：这里严格按照‘需求’来设计 最简产品的功能，最简是重点，这是mvp思维的核心之一
```
## 信号
> 最后的mvp产出的信号可以显示出有关于需求的信号
### 例子：
ai output
```

Airbnb（2007，气垫床）

核心假设：陌生人愿意花钱睡在别人家的气垫床上（而不是只有酒店一个选项）。
最小动作：创始人在自己公寓放了三张气垫床，拍了几张照片挂在一个极简网站上，专门给当地一个设计大会的参会者提供"床 + 早餐"。没有支付系统（线下收钱）、没有地图、没有搜索、没有评价。
验证信号：有 3 个人真的预订了。证明"共享住宿"这个需求存在，可以继续投入。
砍掉的：支付、地图、搜索、房主审核、评价系统、保险——全都没做。
Notion（2013 前后）

核心假设：人们愿意用一个"足够灵活的工具"替换掉一堆分散的工具（文档、表格、清单各自一个 App）。
最小动作：早期就是一个"能嵌套的块状编辑器"——能打字、能建页面、页面之间能互相链接。没有数据库、没有协作、没有模板市场。
验证信号：早期用户愿意天天用它记笔记，而不是用几天就丢。
注意：Notion 其实是最不"标准 MVP"的一个——它花了几年反复重写才长成今天这样。它恰恰说明"最小"不等于"一次做对"，而是要找到一个值得反复打磨的核心。
Supabase（2020）

核心假设：开发者想要一个"开源的 Firebase 替代品"——不想被 Firebase 锁死，但又想要"数据库直接变后端"的体验。
最小动作：在 Postgres 数据库上套一层 REST/实时 API，让开发者拿到一个数据库就能立刻用。Dashboard、边缘函数、完整认证 UI 都没做。
验证信号：开源仓库的 star 快速上涨，开发者真的把它接进自己的项目里用了。
```
> 总结：这些例子全部都遵循这样的一套公式：  
> 核心假设 → 最小动作 → 信号  
> 这就是mvp现实中践行的思路
### 标准
信号反应的是需求是否真的存在，比如例子中的‘开源仓库的 star 快速上涨’就证明有人真的有这个需求。反之没有反响就表示这个产品的‘假设’被验证为否，也就是说市场不存在或者太小
## 练习：
> 题目：列出3个mvp的核心功能，以及>=5个的要砍掉的功能
### 解答
```
产品核心假设：有人愿意为了打破当今社会随处不在的信息茧房而付出时间（显示出使用意愿）（茧房的来源可以是 算法 可以是 政治 可以是 自身喜好）
产品的核心功能===
1. ai信息总结媒体信息功能（最重要不显示信息没有意义）
2. 透明个性化测试功能，最有冲击力&吸引力，让使用者一下就意识到茧房的存在以及其可怕
3. 茧房算法，个性化定义茧房，反向推送。
砍掉的功能===
1. 华丽的ui，ui耗时且和核心假设没有直接关系
2. 背景音乐，干不过音乐软件
3. 个性化字体，能看到信息就行，没有必要加这个
4. ai助手，不需要一个独立出来的ai助手，很多软件都有这个鬼，事实上压根用不到只觉得烦
5. 开屏广告，直接把第一批受试者吓跑了，这个阶段根本不用为了这种蝇头小利做这种因小失大的事
```
> 判断：使用意愿不是抽象概念，而是需要量化的标准，符合标准：假设成立，反之：推翻假设。在这个练习中的假设量化就是，用户中>=20%的人每天使用时常>=20分钟
