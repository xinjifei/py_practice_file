## 1. uv — 包管理与虚拟环境

### 是什么
> 让每个项目有自己独立的 Python 环境和依赖，不互相打架。

### 什么时候用
- 开新项目的第一件事
- 拿到别人的代码，运行报 `ModuleNotFoundError` 时 → `uv sync`
- 需要装新库时 → `uv add`，不是 `pip install`

### 对 AI 的提示词
> "帮我用 uv 初始化项目，需要 pandas 和 python-dateutil"

### 审 AI 输出的 3 个点
1. `pyproject.toml` 里 `requires-python` 对吗？（你装的是 3.10 还是 3.12？）
2. 依赖有写版本下界吗？（`pandas>=2.0`，不要写成 `*` 或没写）
3. `.venv/` 被 `.gitignore` 忽略了吗？（AI 有时候忘了）

### ⚠️ 我目前的薄弱点
- 还没试过 `uv lock` 和 lockfile 的作用——知道有这个东西就行，碰到依赖冲突时知道该问 AI "帮我检查 lockfile"

## 2. Git — 版本控制

### 是什么
> 代码的"存档系统"——每次 commit 都是一个可回退的存档点。

### 什么时候用
- 写完一个可运行的小功能 → commit
- 准备改一个大东西之前 → commit（这样改坏了能回退）
- 代码突然坏了，想回到昨天的版本 → `git log` 找存档点
- 不确定自己改了什么 → `git diff` 或 `git status`

### 对 AI 的提示词
> "帮我写 .gitignore，忽略 .venv、__pycache__、.pytest_cache"
> "我现在想回退到上一个 commit，但保留现在的改动，怎么写命令"

### 审 AI 输出的 3 个点
1. AI 给的 `git reset` 命令带 `--hard` 了吗？（带了这个会删代码，确认前别执行）
2. `.gitignore` 有没有漏 `.venv/`？（这是最大的文件夹，没忽略的话 git 会卡死）
3. commit message 是 AI 写的吗？改成你自己的一句话——commit message 是写给你三个月后看的

### ⚠️ 我目前的薄弱点
- 练习只做了 init → add → commit 一条直线。**最需要补的一个操作：**
  > 故意改错一行 → `git diff` 看改动 → `git restore <文件名>` 回退单个文件
- 这个操作在日常里比 commit 还高频

## 3. typing — 类型注解

### 是什么
> 告诉人和 IDE "这个参数应该传什么类型、这个函数返回什么类型"。不影响运行，只影响可读性。

### 什么时候用
- 函数给别人（或三个月后的自己）用的时候
- 函数参数超过 2 个的时候（不写类型，调用方根本不知道要传什么）
- 返回值是一个复杂结构的时候（tuple / dict / list of dicts）

### 对 AI 的提示词
> "给这个项目里的所有函数都加上类型注解"
> "这个函数返回一个 tuple，帮我标注每个位置是什么类型"

### 审 AI 输出的 3 个点
1. `dict` 还是 `Dict`？Python 3.9+ 用小写 `dict`，AI 有时候给旧写法 `Dict`
2. 返回值类型和实际 return 对得上吗？AI 可能写 `-> pd.DataFrame` 但实际 return 是一个 tuple
3. `Optional` 用了吗？如果一个参数可以传 `None`，应该写成 `Optional[str]` 而不是 `str`

### ⚠️ 我目前的薄弱点
- 还不会看 mypy 或 pyright 的报错——这些工具能自动检查类型对不对。下次可以让 AI 帮你跑一次 mypy，然后让它解释报错。

## 4. logging — 结构化日志

### 是什么
> 比 print 高级的"程序说话方式"——带时间戳、带等级、可以一键调音量（只显示错误，不显示调试信息）。

### 什么时候用
- 任何会长期运行的程序（定时任务、web 服务、数据管道）→ **必须用**
- 有一段代码老是间歇性出错，需要看"出错前发生了什么" → 加 DEBUG 日志
- 程序正式上线前 → 把调试用的 print 全部删掉或换成 logging

### 对 AI 的提示词
> "把这个文件里的 print 全部替换成 logging，按重要程度分好级别"
> "帮我配置 logging，同时输出到终端和文件，文件保留最近 7 天"

### 审 AI 输出的 3 个点
1. 日志级别用对了吗？（正常流程 INFO，可能的问题 WARNING，明确错误 ERROR——AI 容易全写 INFO）
2. `basicConfig` 是放在**程序入口**吗？（不是放在工具函数里——这个 AI 有时候会搞错位置）
3. format 里有时间戳吗？没有时间戳的日志基本没用

### ⚠️ 我目前的薄弱点
- 只练了 basicConfig 输出到终端。**生产环境真正用的是**：
  - `logging.FileHandler` → 输出到文件
  - `logging.handlers.RotatingFileHandler` → 文件太大了自动切分
  - 需要的时候问 AI："帮我把日志配置改成同时输出终端 + 文件，文件自动轮转"

## 5. pytest — 测试基础

### 是什么
> 自动运行你写的测试函数，告诉你哪个过了哪个挂了。

### 什么时候用
- 写完一个函数之后 → 立即写测试（不是"等整个项目写完再补"）
- 改了一个老函数 → 先跑测试，看有没有改坏别的地方
- 修了一个 bug → 先写一个能复现这个 bug 的测试，确认修好了再提交

### 对 AI 的提示词
> "给这个 clean_df 函数写 pytest 测试，覆盖正常数据、空数据、有 NaN 的数据、全 NaN 的数据"
> "帮我把测试按功能拆成不同文件，放在 tests/ 目录下"

### 审 AI 输出的 3 个点
1. 测试函数名以 `test_` 开头了吗？（不这么写 pytest 发现不了）
2. 边界情况够吗？（空输入、全是脏数据、极大值——AI 倾向于只写"正常情况"）
3. `assert` 后面的错误提示写了吗？（`assert result == 3, f"期望3行，实际{result.shape[0]}行"`——没写错误提示的 assert，挂了你看不懂）

### ⚠️ 我目前的薄弱点
- 还没跑过 `uv run pytest -v`（带 `-v` 显示每个测试的名字，带 `--tb=short` 缩短报错信息）
- 还没用过 `pytest --cov` 看"哪些代码没被测试覆盖"——后续可以让 AI 帮你配置

## 6. parametrize — 参数化测试

### 是什么
> 几十个测试函数逻辑一样、只是输入输出不同 → 合并成一个函数，用一张表驱动。pytest 的两个工具：
> - `@pytest.mark.parametrize` → 一组数据自动生成 N 个测试
> - `@pytest.fixture` → 多个测试共享同一份测试数据

### 什么时候用
- 写第 3 个"除了数据不一样其他全一样"的测试函数时 → 停下来，改用 parametrize
- 多个测试函数里出现一模一样的 DataFrame 构造代码 → 抽成 fixture 放到 conftest.py
- 产品经理说"再加 5 个边界情况" → 加 5 行数据，不用写 5 个函数

### 对 AI 的提示词
> "这几个测试函数逻辑一样，帮我用 parametrize 合并"
> "把这段重复的测试数据抽成 fixture 放到 conftest.py"
> "给这个参数化测试加 3 个边界情况的用例"

### 审 AI 输出的 3 个点
1. 参数名和函数签名一致吗？（`"a, b"` 配 `def test(a, b)` — 名字对不上 pytest 直接报错）
2. `pytest.param` 的 `id` 写了吗？（没写的话，pytest 输出里你分不清是哪个用例挂了）
3. fixture 放在 conftest.py 了吗？（AI 有时候直接塞在当前文件末尾——也能跑，但不合规范）

### ⚠️ 对 parametrize 的心态校准
> **不需要从零手写，但需要能从 AI 输出中看出问题。**
> 你只需要会：① 认出"这段测试重复了，该参数化" ② 读 AI 给的 parametrize 代码，确认参数名对、用例全、id 有写
> 至于语法——每次让 AI 写就行。

## 🧠 六个工具一张图：什么场景该叫 AI 干什么

```
项目启动
  │
  ├─→ "uv init + 写 pyproject.toml"          ← 叫 AI
  ├─→ "写 .gitignore"                        ← 叫 AI
  │
代码编写
  │
  ├─→ "给函数加类型注解"                     ← 叫 AI
  ├─→ "把 print 换成 logging"               ← 叫 AI（或自己写，模板固定）
  │
每完成一个函数
  │
  ├─→ "写 pytest 测试，覆盖边界情况"          ← 叫 AI
  ├─→ git add → git commit                  ← 自己来（10秒的事）
  │
发现测试重复了
  │
  ├─→ "用 parametrize 合并"                  ← 叫 AI
  ├─→ "把公共数据抽成 fixture"               ← 叫 AI
  │
改出 bug 了
  │
  ├─→ git diff / git restore                ← 自己来
  ├─→ "这段 diff 帮我看，问题在哪"           ← 叫 AI
  │
上线前
  │
  ├─→ uv run pytest -v                      ← 自己来（一条命令）
  └─→ "帮我看哪些代码还没被测试覆盖"          ← 叫 AI
```
