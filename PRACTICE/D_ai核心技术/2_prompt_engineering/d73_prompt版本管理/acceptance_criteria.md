## AI 分界线
- **归你（必须长在脑子里）**：
  - **为什么 prompt 要进 Git**——具体丢了什么：改动历史、改的原因、改的效果。在聊天窗口里改 prompt，等于**每次都在重写，而且不记得上次为什么改**。这是判断力无法累积的根因
  - **A/B 测试的变量控制**——一次只放一个变量动。这条不能外包：跑对比的脚本 AI 能写，但"我这次对比的结论到底成不成立"只有你能判。接 d68 的 temperature（要锁 0）、接 d72 的三把尺子（要拿它当判据）
  - **"改完变好了"这个结论什么时候不可信**——只跑了一条样本、换了个温度、或者拿测试集本身反复调 prompt（过拟合）。AI 不会提醒你这些
  - **模板的抽象边界**——哪些该做成 `{变量}`（每次都变的：具体数据），哪些必须写死（不变的：规则、格式、禁止项）
- **可外包（概念要知道、实现交给 AI）**：
  - Git 命令本身（`git log` / `git diff` / `git commit` 的具体参数）
  - 目录怎么组织、文件怎么命名
  - A/B 跑分脚本的循环、打印、表格美化的代码
  - `str.format()` 的语法细节

## 硬线（不过不能结束，达标看 note.md 写没写到位）
- [ ] 硬线1：**Prompt 当代码管，管的是三件事**——能说清「独立文件」「Git 追踪」「模板复用」各自解决了什么问题。核心要说透**在聊天窗口里改 prompt 丢了什么**：改动历史没了、改动原因没了、两版效果没法比，所以**每一次改动都不可累积**——这是和"随便聊聊"的根本区别
- [ ] 硬线2：**A/B 测试的变量控制**——能说清要对比两个 prompt 版本，必须锁死哪些东西（模型、temperature、测试样本），以及**为什么**。至少举一个"没锁死会得出什么错结论"的例子。串联两处：d68 的 temperature（锁 0，否则分不清差异来自版本还是随机性）、d72 的三把尺子（"哪个版本更好"要有**判据**，否则比不出结论）
- [ ] 硬线3：**`{变量}` 模板化的意义**——能说清占位符是在切分"**不变的骨架**（任务、规则、输出格式、禁止项）"和"**每次变的数据**"。并说清什么样的 prompt 适合做成模板（会被反复调用、只有输入在变），什么样的不值得（一次性任务）
