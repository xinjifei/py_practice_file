# 第 71 天验收标准

## 体系定位
- 所处阶段：阶段四「AI 核心技术」› Prompt Engineering 在量化场景中的应用，第 2/4 天（同 section，**不跨组**）。
- 前面铺了什么：d70 给出了 `指令 + 例子 + 格式` 三段结构——那是「怎么让 AI 吐出我想要的样子」。也就是**设计指令**。
- 今天的概念：d70 假设「说清楚了它就会照做」，今天把这个假设打破——**说清楚了它也可能不照做**。于是出现三件新事：字段要带**定义/口径**、格式约束要分**层**、代码里必须有**校验 + 重试**兜底。这是「AI 输出不可靠」这个视角第一次出现——从「设计指令」进到「**工程设防**」。
- 和目标的关系：AI 协作能力里的「审 AI 输出」那一半 + 技术判断力。判断力落点：拿到一个不稳定输出，能不能判断**该在哪一层修**——是 Prompt 写得不够死？还是该上 API 的结构化约束？还是只能代码兜底重试？这三层的取舍就是今天真正要长出来的东西。
- **后续两天的依赖**：d73（Prompt 版本管理：对比不同版本的输出质量）**硬依赖**今天的字段定义 + 格式模板——没有明确的输出规格，就无所谓「哪个版本更好」，A/B 对比根本无从谈起。d72（Few-shot 让 AI 模仿策略模式，「必须能写成可执行规则才算合格」）吃今天的直觉：**AI 的输出最终要能被程序/规则接住，不是看着像就行**。d72 的 Few-shot 招式本身来自 d70，不是今天。

## AI 分界线
- **归你（必须长在脑子里）**： 
  - **字段定义 ≠ 字段名**：写「毛利率」不够，得写「毛利率 =（营收 − 营业成本）/ 营收，百分数，保留 1 位」。字段边界靠**定义**划，不靠字段名划——AI 猜不到你的口径
  - **格式约束的三层防线**及各自定位：① Prompt 内约束（字段定义 + 示范 JSON + 反例）② API 层的结构化输出能力（JSON mode / structured output）③ 代码层 `json.loads` + 校验 + 重试。哪层管什么、哪层会怎么失效（①靠概率遵守、②只保证「是合法 JSON」不保证「字段齐」、③是兜底不是解法）
  - **「能解析」不等于「能用」**：结构合法（能 parse、字段齐）只是第一关，还有语义关（单位对不对、口径一致不一致、数值合不合理）。校验要分两层看
  - **重试是兜底，不是解决方案**：出错的根因在约束侧，重试只是把「不可控」变成「可控的失败率」。同一条 Prompt 反复重试，失败率不会下降
- **可外包（概念要知道、实现交给 AI）**：
  - JSON schema 的具体设计、字段命名风格
  - `try-except` / 重试循环的具体语法（下面对应固定写法模板，照抄即可——纯语法，没有概念层可穿透）
  - 正则、`json.loads` 的异常类型选择等实现细节
