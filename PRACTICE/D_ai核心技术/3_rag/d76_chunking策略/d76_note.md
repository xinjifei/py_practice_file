# d76 chunking策略
> RAG检索对象的最小单元
## chunk是什么
- 昨天学习了rag整套系统的大概原理，今天进入它的底层，学习它的一个细分
- RAG在进行写入时，如果按照昨天的笔记，会误认为输入文本就是一整篇文章。但事实上并不是这样的，不能直接把一篇上万字的文章硬塞到一个向量里面，所以并不是一个文章对应一个最小检索目标，这个目标的名字叫“chunk”
- 一个chunk对应一个向量、一个metadata、id，而非一篇文章
## chunk文本分割
- chunk文本的长度过长过短都会有问题
    1. 过长：向量维度数量固定，相对应的可以承载的信息也固定，向量并不会因为文本蕴含很多信息（很长）而增加维度，只能将信息稀释。最后检索不到正确的chunk
    2. 过短：这时文本本身信息量不会再被稀释了，但是对于自然语言，上下文也很重要，如果一个需要一个完整上下文的信息被截断，那么他所蕴含的信息也会因此损失
    
### 分割方法
1. 固定长度：最简单，就是固定字符数量，但是上下文信息容易被截断
2. 按照段落：单单从语义上来讲最能保证代表作者的意思，但是容易长度过长，碰到刚才说的“过长”稀释问题
3. 递归：综合上面两个的方法，在“限制字数”和“保全上下文”中取得平衡
伪代码：
```
def 递归分块(原文，分隔符序列[优先级从高到低：换行段落、单行换行、句号、逗号、空格]，最大块长度，重叠长度)
    取当前最高优先级分隔符
    用这个分隔符把原文拆开，得到若干片段
    遍历每一个片段：
        if 片段长度 ≤ 最大块长度：
            直接把这个片段收入结果列表
        if 片段超长，并且还有更低一级的分隔符可用：
            把这个片段，送入递归分块，改用【下一级更细的分隔符】继续拆分
            将拆分出来的小块并入结果列表
        if 片段超长，已经是最后一级分隔符：
            强制硬切：每次截取最大长度的文本存入结果
            剩余文本向前保留重叠部分，循环截取直到处理完毕
    return 全部分块结果
```
> 现象：分割的方法决定了chunk的内容，而检索是通过匹配内容进行召回的。最后表现为同一个数据、同一个问题，但是因为分割法的不同，返回的结果也不同
### overlap
- 为了进一步防止分割后的chunk出现边界断裂的情况，可以直接给chunk预留重复的空间，用冗余换减小边界断裂的风险
- 但是它的冗余也是代价，而且可能出现“重复召回”（两个chunk因为重叠同时含有类似信息）
