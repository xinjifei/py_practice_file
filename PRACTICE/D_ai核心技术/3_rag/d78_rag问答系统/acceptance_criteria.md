## 硬线（不过不能结束，达标看 note.md 写没写到位）
- [ ] **硬线1 · 四步流程与故障归因**：把 RAG 四步——问题 Embedding → 向量检索 top-k → 拼 Prompt → LLM 生成——逐个写成「输入是什么 → 输出是什么」。再写清三种典型坏症状分别该先怀疑哪一步：
  ① 答案自信但和你的文档无关（检索没捞到？还是捞到了却没放进 prompt？）
  ② 答案内容对、但引用标错了文档/页码（引用是从哪来的？模型编的还是有据可查？）
  ③ 文档里明明有答案，模型却说「不知道」（问题措辞和文档差太远？top-k 太小？切断了上下文？）
  只写「先检索再生成」不算。
- [ ] **硬线2 · RAG 的本质与边界**：用自己的话说清 RAG 不是让模型变聪明，而是「回答问题前先翻一下你给的小抄」——模型权重一点没变，变的是上下文里多了你塞进去的文本。据此写清它解决什么（训练截止日期、私有数据、来源可追溯）、不解决什么（推理能力、判断力），并给出一个**「这个问题不需要 RAG」的具体例子**及理由。
- [ ] **硬线3 · 有/无 RAG 差异归因 + 引用可验证**：对同一个问题分别问「无 RAG」和「有 RAG」，写出差异的具体表现（无 RAG：泛泛而谈 / 编造具体数字 / 干脆说不知道；有 RAG：能落到具体文档和数字），并把差异归因到「模型这次看到了哪段文本」，不是「模型变聪明了」。同时说清引用怎么保证真实：引用只能取自检索结果的 metadata（source、chunk_index），并且要能回到原文核对「这段文字是否真的支持这个结论」——写出你实际打算怎么核对。
