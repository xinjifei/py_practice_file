# 第 77 天验收标准

## 体系定位
- 阶段四「AI 核心技术」›「RAG 检索增强生成」第 3/6 天（75–80，其中 79、80 是复习/缓冲日）。
- 前接第 75 天「能存能查」、第 76 天「切什么、怎么切」。今天不是学新概念，是把两者接成一条完整流水线：**取文档 → 清洗 → 分块 → 向量化 → 入库 → 检索验证**。
- 后续第 78 天直接在这个知识库上做「检索 + LLM 生成」，第 79、80 天的复习主题就是「确认知识库检索质量达标」。今天这条链建歪了，78 天的答案再会调 prompt 也救不回来。
- 能力拼图：**拆解能力 + AI 协作能力**——把一整条链路拆成几个可独立指挥、可独立验收的段落；能判断 AI 写的东西对不对，而不是「跑通了就算完」。
 
## AI 分界线
- **归你（必须长在脑子里）**：链路每个环节的输入/输出/失败症状；「检索成功」的判定标准；从现象反推是哪个环节坏了；不靠「程序没报错」而是靠哪几个数验收 AI 的产出。
- **可外包（概念知道、实现交给 AI）**：PDF 解析库的具体调用、清洗正则的写法、embedding 模型的参数、ChromaDB 的 API 签名、脚本骨架本身。

> 说明：今天按你的要求把重心从「概念背下来」移到「链路能指挥、故障能定位」。硬线 3 条，都不要求复述定义——前两条要指着具体现象说原因和下一步，第三条把今天接回前几天的理解。

## 硬线（不过不能结束，达标看 note.md 写没写到位）
- [ ] **硬线1 · 链路地图**：把六个环节逐个写成「输入是什么 → 输出是什么 → 这一步坏了会看到什么现象」。要求是能**凭现象反推环节**，比如「某份文档只切出 1 块」→ 分块或清洗环节；「5 个问题全部命中同一份文档」→ 分块或 embedding 环节；「明明有答案却检不出」→ 清洗/切分/问题措辞三选一，要能说出你优先怀疑哪个、为什么。只写「清洗很重要」这种结论不算。
- [ ] **硬线2 · 检索质量的判定与归因**：说清「什么算检索成功」的判定方法——最低标准是 top-3 里至少有 1 条能回答；更硬的自动化判据是**你已经知道答案在哪份文档里，看那份文档在不在 top-3、排第几**。再说清失败时怎么归因：chunk 太大（信息稀释）/ 太小（上下文断裂）/ 清洗没干净（页眉页脚混进向量）/ embedding 模型和语料语言不匹配 / 问题措辞和文档措辞距离太远。要能对你自己的 5 个问题里至少 1 个「不相关」给出**具体归因 + 下一步打算调哪一个参数**，而不是「再试试」。
- [ ] **硬线3 · 串联**：把今天这条链的每一步对回前几天学的概念——哪一步在用第 75 天的向量与距离、哪一步在用第 76 天的 chunk 边界与重叠、embedding 那一步和你更早学的 token / 向量是什么关系。再写清今天哪一步你最没把握（或真卡住了），原因是不是前面某天的理解不到位——要具体到点，不能写「都还好」。

## 代码练习（少量；代码可以让 AI 写，但你要看得懂、能指挥、能验收）
- [ ] 练习1：用你自己的 ≥10 份文档（研报/财报/新闻/网页，PDF 转文本也行）跑通全链，输出中间产物统计：文档数、chunk 总数、平均块长、最长块长、每份文档产出多少块。对任何异常（某文档只出 1 块、块长贴着上限、块数远少于预期）都能解释是哪个环节造成的。
- [ ] 练习2：准备 5 个**你先知道答案**的问题，给每个问题标上「答案应该在哪份文档」。跑 Top-3，记录命中的 source 与距离，标注 相关 / 部分相关 / 不相关。对至少 1 个失败的问题给出归因（哪个环节）和下一步要调的参数——**只写判断，不必真调**。
